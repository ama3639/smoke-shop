# راه‌اندازی و نگهداری نسخه پایه

نسخه: 0.7.0 · تاریخ: 2026-10-11

## نصب در ویندوز

Python 3.12 یا جدیدتر و Node.js 22 یا جدیدتر (ترجیحاً LTS) نصب باشد. اجرای محلی به Docker، Redis، کلید AI یا سرویس پرداخت نیاز ندارد.

```powershell
Set-Location D:\Smokeshop
py -3.12 scripts/setup.py
py -3.12 scripts/dev.py
```

setup محیط مجازی Python و وابستگی‌های قفل‌شده را نصب می‌کند، migration و نقش‌ها را اعمال می‌کند و ۱۴ مدل وینستون با تصویر ارسالی فروشنده برای معرفی عرضه حضوری می‌سازد. اجرای مجدد، تصویر داخل مخزن را برای مدل‌های قبلیِ فاقد آن ثبت می‌کند و اطلاعات نمونهٔ دست‌نخورده را ارتقا می‌دهد؛ ویرایش‌های فروشنده، تصویر آپلودشده، موجودی و قیمت حفظ می‌شوند و فروش آنلاین فعال نمی‌شود. کالاهای اکسسوری نسخه قبلی حفظ می‌شوند و صفحه اصلی همه انواع کالا را با صفحه‌بندی نشان می‌دهد. منبع گروه برند JTI فقط برای Winston فاقد منبع ثبت می‌شود؛ مشخصات نامعلوم حدس زده نمی‌شوند. نصب به PyPI و npm نیاز دارد.

dev دو سرویس را اجرا می‌کند. فروشگاه در `http://localhost:3000` و مدیریت در `http://localhost:8000/admin/` است. Ctrl+C سرویس‌های همین اجرا را متوقف می‌کند. پورت‌های 3000 و 8000 باید آزاد باشند. بک‌اند با `--noreload` اجرا می‌شود؛ بعد از تغییر کد Python این اسکریپت را دوباره اجرا کنید. فرانت‌اند تغییرات را خودکار اعمال می‌کند.

ساخت مدیر (یک‌بار؛ رمز تعاملی و بدون ذخیره در Git):

```powershell
.\backend\.venv\Scripts\python.exe backend\manage.py createsuperuser
```

برای کاربران ادمین از Users گزینه Staff و گروه مناسب را تعیین کنید. نقش‌های Marketplace manager، Seller و Order operator نیز با seed_roles ساخته می‌شوند؛ اعضای فروشنده را در Vendor تعیین کنید. [راهنمای ادمین و تفکیک دسترسی](../user/ADMIN_GUIDE.md). `Catalog editor` مشخصات و موجودی را مدیریت می‌کند؛ تأیید حقوقی و فعال‌سازی عرضه برای `Legal reviewer` و superuser است.

## کاتالوگ و عرضه

در ادمین دسته، کالا، تصویر JPG/PNG/WebP، مدل، رابطه سازگاری و شعبه را ثبت کنید. وضعیت پیش‌فرض کالا `REVIEW_REQUIRED` است و در API عمومی دیده نمی‌شود. `CATALOG_ONLY` کاتالوگ بدون خرید است. `IN_PERSON_ONLY` معرفی عرضه حضوری است؛ `BLOCKED` و کالاهای غیرفعال از API عمومی حذف می‌شوند.

نام ۱۴ مدل از تصاویر فروشنده تطبیق داده شده است؛ شناسه‌های `DEMO-CIG-*` هنوز شناسه داخلی‌اند. موجودی و اطلاعات عرضه باید تأیید شوند. تعداد نخ/بسته و بسته/باکس تأییدنشده با `null` ثبت می‌شوند و در مشخصات «تأیید نشده» نمایش می‌یابند. این مقادیر را پس از بررسی کالای واقعی در ادمین تکمیل کنید.

برای افزودن برند، در Products نوع مناسب (`اکسسوری`، `سیگار`، `سایر دخانیات` یا `سایر کالاها`) را انتخاب کنید و نام برند، تعداد نخ در بسته، تعداد بسته در کارتن و عرضه تکی/عمده را ثبت کنید. نام برند یکسان وارد شود تا فیلترها گروه‌بندی درست داشته باشند. صفحه اصلی برندهای ثبت‌شده را از داده کاتالوگ می‌گیرد؛ صحنه آغازین فعلاً وینستون است. عرضه تکی یعنی بسته، نه نخ منفرد. قیمت‌گذاری عمده، ثبت درخواست همکاری و خرید اینترنتی سیگار در این نسخه پیاده نشده‌اند.

سیگار و سایر دخانیات در مدیریت نمی‌توانند `APPROVED_ONLINE` شود و حتی تغییر اشتباه مستقیم داده آن را در API قابل خرید نمی‌کند. برای معرفی حضوری از `IN_PERSON_ONLY` استفاده کنید. شروط خرید زیر فقط به اقلام غیردخانی مربوط‌اند.

خرید به این شروط نیاز دارد: `APPROVED_ONLINE` با مرجع کتبی حقوقی، فعال‌بودن فروش دسته، flag با کلید `cart` و قیمت/موجودی معتبر. همه در API بررسی می‌شوند. تأیید سن فقط کنترل کمکی است.

flag با کلید `order_requests` ثبت **درخواست سفارش بدون پرداخت** را فعال می‌کند. قبل از فعال‌کردن، فرآیند بررسی اپراتور و انقضای رزرو را تعیین کنید. درخواست موجودی را رزرو می‌کند، مبلغ و عنوان را از سرور snapshot می‌گیرد و با کلید یکتا از تکرار جلوگیری می‌کند. هیچ درگاه، تأیید پرداخت، ارسال یا تبدیل خودکار به سفارش قطعی وجود ندارد.

لغو رزرو توسط اپراتور و آزادسازی موجودی دقیقاً یک‌بار:

```powershell
.\backend\.venv\Scripts\python.exe backend\manage.py cancel_order UUID-OF-ORDER
```

سفارش‌ها، دفتر موجودی و Audit Log فقط خواندنی‌اند؛ عمل کنترل‌شده لغو معلق برای نقش مجاز در Orders وجود دارد. تغییر قیمت، موجودی، وضعیت حقوقی، دسته و flag ثبت می‌شود. رزرو جدید expires_at با مهلت پیش‌فرض ۳۰ دقیقه دارد (ORDER_RESERVATION_MINUTES). زمان‌بند را جدا تنظیم کنید تا فرمان `expire_orders` با Python همین محیط مثلاً هر دقیقه اجرا شود؛ setup زمان‌بند نمی‌سازد. فرمان موجودی را یک‌بار آزاد می‌کند. رزرو قدیمی بدون مهلت نیازمند بررسی/لغو دستی است. API نشانی یا تلفن مشتری نمی‌گیرد؛ پیگیری مهمان فقط با نشست همان مرورگر ممکن است.

## نگهداری و به‌روزرسانی

سرویس‌ها را متوقف کنید و پیش از migration از داده‌ها backup بگیرید. هنگام توقف از `backend/db.sqlite3`، `backend/media/` و `backend/.local-secret` نسخه پشتیبان امن تهیه کنید. این فایل‌ها نباید وارد Git شوند. بازیابی backup را روی محیط مجزا آزمایش کنید.

```powershell
Set-Location D:\Smokeshop
git status --short
git pull --ff-only origin main
py -3.12 scripts/setup.py
py -3.12 scripts/dev.py
```

`--ff-only` در تاریخچه واگرا متوقف می‌شود؛ تغییرات محلی را پیش از pull حفظ کنید. نصب مجدد داده‌ها را حذف نمی‌کند.

برای پاک‌سازی نشست‌های منقضی، `backend/manage.py clearsessions` را با Python محیط مجازی اجرا کنید. این فرمان سبدها و سفارش‌ها را حذف نمی‌کند؛ سیاست نگهداری آن‌ها پیش از عرضه عمومی باید تعیین و اجرا شود.

## تست و build

دود/فیلم سراسری و پوستر آن در نسخه 0.7.0 از مسیر نمایش حذف شده‌اند. فایل‌ها برای تاریخچه دارایی حفظ‌اند و دانلود نمی‌شوند. `.hero-atmosphere` فقط در بخش معرفی خطوط SVG ظریف دارد؛ بدون blur یا لایه ثابت. توقف دستی و reduced-motion آن را ثابت می‌کنند.

۱۴ تصویر PNG ارسالی در `frontend/public/images/products/winston/` حفظ شده‌اند؛ نسخه‌های سبک WebP در زیرپوشه `optimized/` با همان ابعاد 1122×1402 قرار دارند. فهرست و صفحه محصول، قاب کامل عکس را با `object-fit: contain` نمایش می‌دهند؛ عکس روی وجوه بسته CSS کشیده نمی‌شود. نگاشت شماره تصویر به مدل در [PRODUCT_IMAGES](../catalog/PRODUCT_IMAGES.md) ثبت است.

فیلد ادمین «مسیر تصویر داخل پروژه» به فایل‌های داخل `/images/` اشاره می‌کند. فیلد تصویر آپلودشده، در صورت وجود بر آن اولویت دارد. `seed_demo` فقط مسیرهای خالی را تکمیل می‌کند؛ مسیر سفارشی و آپلود فروشنده حفظ می‌شود. برای بازتولید فایل‌های سبک پس از تغییر PNGها:

```powershell
.\backend\.venv\Scripts\python.exe scripts\prepare_product_images.py
```

تصویر گروهی هوم‌پیج از `frontend/public/images/hero/winston-collection.png` خوانده می‌شود؛ فایل اصلی در commit `e1e696f` دریافت شده و به‌صورت زمینه روشن یکپارچه، بدون قاب مستقل نمایش داده می‌شود. [راهنمای تعویض عکس](../catalog/HOMEPAGE_IMAGE.md). بخش عمده هنوز مدل CSS دارد؛ عکس باکس دریافت نشده است.

خروج نخ و پیش‌نمایش لمسی حذف شده‌اند. کارت با یک کلیک/لمس یا Enter وارد مشخصات می‌شود؛ تصویر کامل بسته ثابت می‌ماند.

```powershell
.\backend\.venv\Scripts\python.exe backend\manage.py test shop
Set-Location frontend
npm run typecheck
npm run build
npx playwright install chromium
npm run test:e2e
```

E2E از بک‌اند 8010، فرانت‌اند 3010 و دیتابیس موقت استفاده می‌کند؛ flag آزمون وارد داده‌های توسعه نمی‌شود. پنج تست هم‌زمانی در PostgreSQL اجرا و در SQLite با دلیل مشخص skip می‌شوند. CI تست PostgreSQL، build و مرورگر دسکتاپ/موبایل دارد.

## تنظیمات و تولید

تنظیمات Django از متغیرهای فرایند خوانده می‌شوند؛ کپی `.env` به‌تنهایی آن‌ها را اعمال نمی‌کند. پیش‌فرض‌ها برای توسعه کافی‌اند.

| متغیر | کاربرد |
| --- | --- |
| `BACKEND_URL` | آدرس داخلی بک‌اند Next؛ پیش‌فرض `http://127.0.0.1:8000`؛ هنگام build و start یکسان باشد |
| `DJANGO_DEBUG` | پیش‌فرض `1`؛ تولید `0` |
| `DJANGO_SECRET_KEY` | محرمانه و الزامی در تولید؛ توسعه فایل کلید محلی می‌سازد |
| `DJANGO_ALLOWED_HOSTS` | میزبان‌های دقیق Django، جداشده با کاما |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | مبدأ دقیق HTTPS فروشگاه و ادمین، جداشده با کاما |
| `DATABASE_URL` | اتصال PostgreSQL؛ در تولید الزامی |
| `DB_SSLMODE` | پیش‌فرض `require`؛ فقط PostgreSQL محلی بدون TLS: `disable` |

SQLite برای توسعه تک‌کاربره است. تولید به PostgreSQL و TLS معتبر نیاز دارد. اجرای تولید: `gunicorn config.wsgi:application` در backend و `npm run build` سپس `npm start` در frontend؛ ابتدا migration و `collectstatic --noinput` اجرا شوند. reverse proxy باید TLS را terminate کند، `/admin/` و `/static/` را به Django/staticfiles و `/media/` را به فضای رسانه پایدار هدایت کند، مسیرهای فروشگاه را به Next بفرستد و headerهای forwarded را از کاربر نپذیرد. بک‌اند باید داخلی بماند.

این نسخه برای توسعه و نمایش پایه است. احراز سن قابل اتکا، 2FA ادمین، پرداخت، آدرس و ارسال، نصب زمان‌بند انقضای رزرو، rate limiting، مانیتورینگ و ممیزی امنیتی تولید هنوز پیاده نشده‌اند. AI سلامت و RAG در این نسخه وجود ندارند. حرکت عکس با اسکرول و خطوط ظریف محلی در بخش معرفی فعال‌اند؛ توقف دستی و تنظیم کاهش حرکت دستگاه آن را به صحنه ثابت تبدیل می‌کنند. عرضه عمومی به تکمیل موارد عملیاتی و تأییدهای واقعی نیاز دارد.


## ارتقای 0.7.0 و عرضه‌های فروشنده

پس از backup و دریافت شاخه موردنظر، setup یا `migrate` سپس `seed_roles` را اجرا کنید. migration 0005 جدول Vendor/Offer و ارتباط nullable به سبد/سفارش/دفتر و expires_at را اضافه می‌کند؛ داده/موجودی قبلی حفظ است. هیچ فروشنده ساختگی برای DB توسعه seed نمی‌شود. نمونه‌های دو فروشنده فقط در دیتابیس موقت E2E هستند.

هر کالا می‌تواند عرضه چند فروشنده با قیمت/موجودی مستقل داشته باشد. به محض وجود Offer، موجودی/قیمت مستقیم Product برای عرضه آن کالا کنار گذاشته می‌شود. فروشنده فعال + عرضه فعال/approved شرط نمایش است؛ سیاست کالا همچنان شرط خرید سرور است. تبدیل کالای دارای رزرو مستقیم به Offers را پس از بررسی/لغو رزروهای قبلی انجام دهید. [قرارداد API](../api/CATALOG_API.md) و [منابع داده](../catalog/PRODUCT_DATA.md).

برای این مرحله شاخه توسعه `feature/catalog-marketplace` است؛ main فقط پس از merge PR به نسخه جدید می‌رسد. روی رایانه دیگر ابتدا `git status --short` و `git fetch origin`، سپس دریافت همان شاخه و `git pull --ff-only`؛ تغییرات محلی را بدون بررسی بازنویسی نکنید. برای تغییر جدید، commit روی شاخه خود و `git push -u origin HEAD` انجام دهید. دستورهای اصلی در این راهنما پس از merge برای main هستند.
